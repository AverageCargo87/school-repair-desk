# Заявки на ремонт — Школа. Техническое задание (MVP)

Веб-сервис (открывается с телефона, ставится на экран «Домой»), где заявители сообщают о неисправностях
в закреплённых зданиях, распределитель назначает исполнителей и сроки, исполнители отмечают выполнение с фото.
Уведомлений в MVP **нет** — только сайт. Интерфейс полностью на русском, простым языком.

Источник требований: рукописная схема + документ «Распределение ролей и закрепление зданий»
(данные — `data/roster.json`) + ответы заказчика (10.10.2026):
- исполнителя **и соисполнителей** назначает распределитель;
- исполнитель **или соисполнитель** может написать распределителю комментарий о проблеме/нехватке ресурсов,
  распределитель сам всё поправляет (переназначает, меняет срок) — отдельного статуса «закупка» нет;
- два заявителя одного здания (Корпус 6, ул. Речная, д. 25) **видят заявки друг друга** — заявитель видит все заявки своих зданий;
- дата выполнения ставится **автоматически** при нажатии «Выполнено»;
- уведомлений пока нет;
- нужна **выгрузка в Excel**.

## Стек (уже в проекте)

Next.js 16 (App Router, Server Actions) · React 19 · TypeScript · Tailwind v4 · Drizzle ORM · PostgreSQL,
локально — PGlite (папка `.pgdata`, Docker не нужен). Взято из проекта учёта питания: `lib/auth.ts`, `lib/crypto.ts`,
`lib/ratelimit.ts`, `components/ui/*`, `db/index.ts`, `db/migrate.ts`.

**ВАЖНО:** это Next.js 16 — API отличаются от привычных. Перед кодом читать `node_modules/next/dist/docs/`
(params/searchParams — Promise, `cookies()` асинхронный, middleware переименован в `proxy.ts`, конфиг server actions и т. д.).

Часовой пояс всего приложения — **Europe/Moscow**. Все «сегодня», сроки, даты в интерфейсе и выгрузке считать и
показывать по Москве (хелперы в `lib/time.ts`, никаких голых `toLocaleDateString()` без `timeZone`).

## Роли

| Роль (enum) | Кто | Видит | Может |
|---|---|---|---|
| `requester` — Заявитель | 6 чел., у каждого 1–3 здания | все заявки **своих зданий** (`user_buildings`) | создать заявку по своему зданию; отменить **свою** заявку, пока она «Новая»; комментировать |
| `dispatcher` — Распределитель | Смирнов Д.Д. | **все** заявки | создать заявку по любому зданию; назначить исполнителя, соисполнителей, срок, комментарий; переназначить; снять флаг проблемы; отклонить; вернуть выполненную в работу; комментировать; выгрузка в Excel |
| `executor` — Исполнитель | 12 чел., без привязки к зданиям | заявки, где он **исполнитель или соисполнитель** | основной исполнитель: «Принял», «Выполнено» (фото + комментарий); основной и соисполнитель: «Сообщить о проблеме», комментировать |
| `admin` — Администратор | разработчик | всё, что распределитель | + управление сотрудниками и зданиями (`/admin`) |

Роль у пользователя одна. Права **проверяются на сервере** в каждом действии и каждом маршруте — не только в UI.

## Данные (Drizzle, `db/schema.ts`)

- `buildings`: id, address (уникальный, текст как в документе), active.
- `users`: id, full_name, login (уникальный, латиница, нижний регистр), role, active, password_hash, login_token_hash, created_at.
- `user_buildings`: user_id, building_id (PK по паре) — закрепление заявителя за зданиями.
- `sessions`: id (sha256 токена), user_id, expires_at, created_at. Срок сессии — 180 дней.
- `requests`:
  - id (serial — это и есть номер заявки «№ 17»), created_at, author_id, building_id;
  - location (text, необязательно — «где именно»: этаж, кабинет), description (text, обязательно);
  - urgency enum: `emergency` «Аварийная», `current` «Текущая», `purchase` «Требует закупки»;
  - status enum: `new` «Новая», `assigned` «Назначена», `in_progress` «В работе», `done` «Выполнена», `rejected` «Отклонена», `cancelled` «Отменена»;
  - executor_id (null до назначения), deadline (date, по Москве), dispatcher_comment (последний комментарий распределителя при назначении);
  - accepted_at, completed_at (ставится сервером при «Выполнено»), completion_comment;
  - problem_open (bool, default false) — есть непрочитанная/нерешённая проблема от исполнителя;
  - updated_at.
- `request_coexecutors`: request_id, user_id (PK по паре).
- `request_photos`: id (uuid/random text), request_id, kind enum `problem` (фото заявителя) | `result` (фото устранения) | `comment` (фото к комментарию/проблеме), file_name, mime, size, uploaded_by, created_at, event_id (nullable — к какому событию приложено).
- `request_events` (история + комментарии, только добавление): id, request_id, actor_id, type enum
  `created | assigned | reassigned | accepted | comment | problem | problem_resolved | completed | rejected | cancelled | reopened`,
  text (комментарий/причина), meta (jsonb: напр. `{executorId, coexecutorIds, deadline}`), created_at.

## Жизненный цикл

```
new ──(распределитель: «Отправить» — исполнитель+срок)──▶ assigned ──(исполнитель: «Принял»)──▶ in_progress ──(исполнитель: «Выполнено» + фото)──▶ done
 │                                                         │  ▲                                    │                                                     │
 │ заявитель: «Отменить» (только своя, только new)         │  └─(распределитель меняет исполнителя → снова assigned)                                     │
 ▼                                                         │                                                                                              │
cancelled            распределитель: «Отклонить» + причина (из new/assigned/in_progress) ──▶ rejected        распределитель: «Вернуть в работу» + комментарий ◀──┘ (done → assigned, исполнитель прежний)
```

Правила:
1. **Назначение** (`new|assigned|in_progress`): исполнитель обязателен (активный `executor`), соисполнители — 0..N других
   активных исполнителей (не равны основному), срок обязателен (дата ≥ сегодня по Москве), комментарий необязателен.
   - из `new` → `assigned`, событие `assigned`;
   - повторное назначение: если сменился основной исполнитель → статус `assigned` (новый должен принять), `accepted_at = null`;
     иначе статус не меняется; событие `reassigned`;
   - любое (пере)назначение снимает `problem_open`.
2. **«Принял»** — только основной исполнитель, только из `assigned` → `in_progress`, `accepted_at = now`.
3. **«Выполнено»** — только основной исполнитель, только из `in_progress`. Минимум **1 фото** результата, комментарий необязателен.
   `completed_at = now` (сервер), `problem_open = false`, событие `completed`.
4. **«Сообщить о проблеме»** — основной исполнитель или соисполнитель, в статусах `assigned|in_progress`. Текст обязателен,
   до 3 фото. Ставит `problem_open = true`, статус не меняет, событие `problem`. Распределитель видит заявку в начале списка с меткой
   «Проблема». Снимается: (пере)назначением, кнопкой распределителя «Проблема решена» (событие `problem_resolved`, можно с комментарием),
   выполнением, отклонением.
5. **Комментарий** — любой, кто видит заявку, в любом статусе; текст обязателен, до 3 фото. Событие `comment`.
6. **Отмена** — автор-заявитель, только `new` → `cancelled`.
7. **Отклонить** — распределитель/админ, из `new|assigned|in_progress`, причина обязательна → `rejected`.
8. **Вернуть в работу** — распределитель/админ, из `done` → `assigned` (исполнитель и соисполнители прежние, срок можно поменять,
   комментарий обязателен), `completed_at = null`, `accepted_at = null`, событие `reopened`.
9. **Просрочка** — не статус, вычисляемый признак: `deadline < сегодня (МСК)` и статус `assigned|in_progress`. Показывать красным «Просрочена».

## Фото

- Выбор: `<input type="file" accept="image/*" multiple>` (на телефоне предложит камеру или галерею).
- **На клиенте** сжимать через canvas: длинная сторона ≤ 1600 px, JPEG quality ≈ 0.8 (это заодно убирает EXIF/геометку).
  Если картинку не удалось декодировать — отправлять оригинал, если он ≤ 8 МБ.
- Лимиты: заявка — до 5 фото, «Выполнено» — 1..5, проблема/комментарий — до 3. Сервер проверяет mime (jpeg/png/webp/heic/heif),
  размер ≤ 8 МБ на файл, количество.
- Хранение: каталог из `UPLOAD_DIR` (по умолчанию `./uploads`, в `.gitignore`), имя файла — случайный id. В `public/` не класть.
- Отдача: `GET /photos/[id]` — только тем, кто видит заявку; `Cache-Control: private, max-age=86400`.
- Server Actions по умолчанию режут тело на 1 МБ — поднять лимит в `next.config.ts` (посмотреть актуальный ключ в доках Next 16) до ~30 МБ.

## Вход

- `/login`: поле «Логин» (не email!) + «Пароль». Rate limit по логину (уже есть `lib/ratelimit.ts`).
- Персональная ссылка `/t/[token]`: **страница** «Вход: Иванова И. И.» с кнопкой «Войти» (POST через server action) —
  GET не должен сам создавать сессию (мессенджеры открывают ссылки для превью). Ссылку выдаёт админ; выпуск новой отзывает старую.
- Логины генерируются транслитом фамилии (`alekseeva`, `mukhina`, `smirnov`…), при совпадении — суффикс с инициалом.
- `/` → редирект по роли: requester → `/my`, dispatcher/admin → `/dispatch`, executor → `/tasks`.

## Экраны

Общее: шапка (название «Заявки», ФИО, роль, «Выйти»), мобильная вёрстка с крупными кнопками (≥ 44 px), ширина ≤ `max-w-2xl`
для рабочих экранов, `max-w-5xl` для списка распределителя и админки. Списки сами обновляются раз в 60 с (`<AutoRefresh/>`).
Карточка заявки в списке (`RequestListItem`): «№ 17», бейдж срочности, адрес, «где именно», описание (2 строки), статус,
срок, «Просрочена», «Проблема», количество фото, дата создания.

1. **Заявитель**
   - `/my` — заявки его зданий; вкладки «Активные» (new/assigned/in_progress) · «Завершённые» (done/rejected/cancelled);
     большая кнопка «+ Новая заявка». Пометка «моя» на своих.
   - `/new` — форма: ФИО и сегодняшняя дата показываются (не редактируются); здание — подставлено, если одно, иначе выбор из
     закреплённых (крупные радиокнопки); «Где именно» (необязательно); «Что случилось» (textarea, обязательно);
     фото (до 5, необязательно); срочность — три крупные кнопки-переключателя (по умолчанию не выбрано, обязательно);
     «Отправить». После отправки — на карточку заявки.
2. **Распределитель / админ**
   - `/dispatch` — все заявки. Сверху счётчики-фильтры: «Новые», «Проблема», «Просрочены», «В работе», «Все активные».
     Фильтры: статус, здание, срочность, исполнитель, поиск по тексту/номеру. Порядок: проблема → новые аварийные → новые →
     просроченные → остальные по дате создания (новые сверху). Кнопки «+ Новая заявка» (любое здание) и «Выгрузка в Excel».
   - Панель на карточке заявки: форма назначения (исполнитель — select, соисполнители — чекбоксы, срок — date, комментарий,
     «Отправить»), «Проблема решена», «Отклонить» (с причиной), «Вернуть в работу» (для done).
   - `/export` — форма: период (по дате создания, по умолчанию текущий месяц), здание, статус → скачивание `.xlsx`
     (`GET /export/file?...`, exceljs). Колонки: №, Создана, Здание, Где именно, Заявитель, Описание, Срочность, Статус,
     Исполнитель, Соисполнители, Срок, Принята, Выполнена, Просрочена (да/нет), Комментарий распределителя,
     Комментарий исполнителя, Последняя проблема. Шапка жирная, закреплена, автофильтр, разумная ширина колонок, даты по МСК.
3. **Исполнитель**
   - `/tasks` — его заявки (основной или соисполнитель — с пометкой «соисполнитель»); вкладки «Активные» · «Выполненные»;
     сортировка: просроченные, затем по сроку.
   - Панель на карточке: «Принял» (assigned) → «Выполнено» (in_progress; форма: фото 1..5 обязательно, комментарий) и
     «Сообщить о проблеме» (текст + до 3 фото). Соисполнитель видит только «Сообщить о проблеме» и комментарии.
4. **Карточка заявки** `/r/[id]` (общая для всех, доступ проверяется): шапка (№, статус, срочность, просрочка, проблема),
   здание + где именно, автор и дата, описание, фото заявителя, назначение (исполнитель, соисполнители, срок, комментарий
   распределителя), результат (дата выполнения, фото, комментарий), **панель действий текущей роли** (сразу здесь, чтобы
   на телефоне не листать через историю), лента истории/комментариев (с фото), форма комментария.
5. **Админ** `/admin/users` — список (ФИО, логин, роль, здания, активен); создать/изменить (ФИО, логин, роль, здания для
   заявителя), «Задать пароль», «Создать ссылку для входа» (показать один раз с кнопкой «Копировать»), отключить/включить.
   `/admin/buildings` — адреса: добавить, переименовать, отключить.

Фото в интерфейсе — сетка миниатюр, по нажатию открывается крупно (новая вкладка или простой лайтбокс).

## Скрипты и данные

- `npm run db:setup` — миграции + **демо-сид**: здания и сотрудники из `data/roster.json`, админ `admin`, всем пароли
  (печатаются в консоль и пишутся в `data/credentials.local.csv`, файл в `.gitignore`), плюс 8–12 демо-заявок во всех статусах
  (обычные хозяйственные поломки, без фото), чтобы экраны не были пустыми.
- `npm run roster:init` — для прода: идемпотентно заводит здания/сотрудников из `data/roster.json` (новым — пароль + ссылка
  в `data/credentials.local.csv`), существующих не трогает.
- `npm test` — тесты сервисного слоя на PGlite в памяти (`node:test` через `tsx --test`).

## Деплой (подготовить, не выполнять)

Небольшой VPS: 80/443 держит Traefik соседнего проекта (сеть `n8n_default`, certresolver из его конфигурации,
маршруты из docker labels). Свой `docker-compose.yml`: сервисы `app` (готовый образ, собранный локально) и `db` (`postgres:16`),
**без Caddy и без проброса портов наружу**, `app` в сети `n8n_default` (external) с labels Traefik, `db` только во внутренней сети;
`mem_limit` (app 320m, db 192m), `TZ=Europe/Moscow`, том для `UPLOAD_DIR` и для БД, логи `max-size: 10m`.
Уникальные имена роутеров/сервисов Traefik (`zayavki`), домен из `DOMAIN` в `.env`.
